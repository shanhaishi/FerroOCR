# FerroOCR · 项目文档库

> **FerroOCR（铁识）** —— Windows 上的「附属式」本地 OCR 组件：**一个 exe**，四级接入阶梯，开箱即用，静默运行。
>
> 当前阶段：**需求阶段（v1.3 草案，待评审）**

---

## 这是什么

不是服务，不是平台，是**一个能被任何程序方便调用的 OCR 能力**。

现代语言一行调用：

```python
from ferroocr import ocr
r = ocr(r"C:\scans\invoice.png")
for line in r.lines:
    print(line.text, line.score)
```

老工具（按键精灵 / 易语言 / aardio）不装任何东西，直接发 HTTP：

```basic
Set http = CreateObject("MSXML2.XMLHTTP")
http.Open "POST", "http://127.0.0.1:1224/ocr", False
http.Send "{""image_path"":""C:\shot.png""}"
```

**没有安装程序、没有配置文件、没有 CUDA、没有依赖。** 唯一的文件就是 `ferroocr.exe`。

---

## 一个包，功能靠启动参数

```bat
ferroocr.exe                       :: 全功能默认姿态：常驻 + HTTP 开 + 管道开
ferroocr.exe --no-http             :: 不要 HTTP（只留管道/命令）
ferroocr.exe --port 8080           :: 固定端口
ferroocr.exe --device gpu          :: 强制 GPU（默认 auto）
ferroocr.exe ocr --image a.png --out r.json   :: 一次性跑完即退
ferroocr.exe --selftest            :: 自检
```

**双击就是全功能**，分发只需要发一个文件。让别的程序改行为也不必改包——`FERRO_ARGS` 环境变量能覆盖同样这些参数。完整参数表见 PRD §5.2.1。

## 四级接入阶梯（核心设计）

同一个 exe，四种调法，**按调用方技术栈选最省事的那级**：

| 级别 | 方式 | 延迟 | 需常驻 | 谁用 |
|---|---|---|---|---|
| **L2** ⭐ | 本地 HTTP `127.0.0.1:1224`（**默认开启**） | ~5–15 ms | ✅ | 按键精灵、易语言、aardio、VBA、AHK、任何语言 |
| **L0** | `ferroocr.exe ocr --image a.png --out r.json` | ~1–2 s | ❌ | 任何语言，零依赖 |
| **L1** | 同上，但请求/结果走文件（拿不到 stdout 时用） | ~1–2 s | ❌ | 拿不到子进程输出的工具 |
| **L3** | Named Pipe `\\.\pipe\ferroocr-v1` | ~1–3 ms | ✅ | Python/C# SDK 内部使用 |

JSON 结构四级完全一致，**换级不用改业务代码**；Python SDK 自动按 L3→L2→L0 降级。

> **L2 默认开启**：因为端口只绑回环，「不暴露网络」这个关端口的理由并不成立；而默认关会逼着每个调用方学会传参数——**老工具的用户不会传参数**。想关的人加 `--no-http` 即可。

## 四条定位（最高约束）

| # | 定位 | 落到需求上 |
|---|---|---|
| **P1** | **附属工具，不是豪华产品** | 接口极简、零配置；宁可少 10 个功能，也不让接入多写 10 行 |
| **P2** | **只做 Windows** | 砍掉 Linux/macOS 适配；放心用命名管道、注册表等专有机制 |
| **P3** | **产物尽可能少** | **只有一个 exe**（CPU+GPU+模型全在内，≤60 MB），不做安装包/Docker，功能差异用启动参数表达 |
| **P4** | **优先被其他程序拉起** | 现代语言走 SDK 自动拉起；老工具走 HTTP 或一次性命令，用完即退 |

## 架构一图

```
调用方程序 (按键精灵 / 易语言 / aardio / Python / C# / 批处理 …)
   │  四级接入阶梯，按自身技术栈选最省事的一级
   │  ├─ L2 本地 HTTP  ─→ POST 127.0.0.1:1224/ocr   ← 默认开启，老工具首选
   │  ├─ L0 一次性进程 ─→ ferroocr.exe ocr --image a.png --out res.json
   │  ├─ L1 命令+文件  ─→ ferroocr.exe ocr --in req.json --out res.json
   │  └─ L3 Named Pipe ─→ \\.\pipe\ferroocr-v1      ← SDK 默认，最快
   ▼
ferroocr.exe —— 唯一的发行物，一个包内含全部能力
   ├─ 双击 / SDK 拉起 / 任何方式启动，默认姿态：常驻 + HTTP 开 + 管道开
   ├─ 功能差异全由启动参数决定（--no-http / --port / --device / --idle …）
   ├─ L0/L1 一次性模式跑完即退，无需常驻 —— 老工具的保底路径
   ├─ 内置模型，首次运行释放到 %LOCALAPPDATA%\FerroOCR\
   ├─ CPU: rusto-nn 纯 Rust SIMD ／ GPU: ONNX Runtime + DirectML（零安装，同一 exe）
   └─ 常驻时空闲 N 分钟自动退出，不占用资源
```

## 需要拍板的问题（PRD §13，剩 6 条）

已落地的五条：✅ 代码签名非阻塞（Q2）、✅ 60 MB 体积可接受（Q3）、✅ 不做截屏识别（Q11）、✅ 老工具清单（Q9）、✅ 只出一个包且 L2 默认开（Q10）。

**代码签名为什么可以放最后**（详见 PRD §12.1）：Windows 弹不弹窗，第一位的不是“有没有签名”，而是这个文件有没有 **Mark of the Web**。浏览器下载、邮件附件会自动打上 `ZoneId=3`，运行前走 SmartScreen 检查；U 盘拷贝、局域网共享、由其他程序释放出来的 exe **不带标记，不弹任何提示**。自行分发的 exe 从未被拦过，原因通常就是走了这条路。另：早年“EV 证书可以立即跳过 SmartScreen”已经失效，花钱买证书也要靠下载量积累声誉。

剩下还需确认的：

1. **GPU 版是否与 CPU 版同批发布？** 现在是一个 exe 内两种引擎（`--device` 切换），建议同批。
2. **典型图片规格**：分辨率、行数、是否扫描件？影响性能目标与默认值。
3. **是否需要自动更新**？v1 不做，文档指引手动替换 exe。
