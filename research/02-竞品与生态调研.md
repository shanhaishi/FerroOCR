## 0. 结论先行（TL;DR）

| 议题 | 结论 |
|---|---|
| **产品空位** | 现有本地 OCR 方案里，**「单二进制零依赖 + HTTP 服务 + 异步任务 + 可观测」四者兼具的基本没有**：Umi-OCR 是桌面 GUI（HTTP 依附进程、无 GPU、无队列）、RapidOCR 是可移植库（API 层是同社区另起的独立小项目、自认不支持并发）、PaddleX/RapidOCRAPI 是 Python + 重依赖。Rust 侧唯一近似竞品是 [deepseek-ocr.rs](https://github.com/TimmyOVO/deepseek-ocr.rs)（2.2k★，Candle + OpenAI 兼容 server），但它绑 VLM 大模型（6.3–9 GB 权重），不是轻量通用 OCR。 |
| **事实标准** | 本地 OCR 服务的 API 已收敛为「**base64/文件上传 → JSON，逐行 `{text, confidence, box}`**」。PaddleOCR HubServing 的 `{status,msg,results}` 与 Umi-OCR 的 `{code,data,time}` 是两个"方言"。**新项目应兼容这两套响应体**（主格式 + 兼容层），而不是另发明一套。 |
| **GPU 路线** | Rust 侧"一套模型 CPU/GPU 通吃"最务实：**纯 Rust CPU（`rusto-nn`/`rten`）+ `wgpu` 覆盖 Win/Linux/macOS 通用 GPU + `cudarc` 做 N 卡服务器加速**；`ort` 仅作可选逃生通道，不做默认依赖。格式不是瓶颈——`rusto-nn` 的三个 loader（`.mnn`/`.onnx`/`.rten`）都产出同一 IR（§B.4）。 |
| **命名** | 推荐 **ferroocr**（首选，五处全空）与 **ferroglance**（品牌名备选，五处全空）。详见 §C。 |
| **最大风险** | 不是算法，是**许可证与模型分发**（Surya 权重 OpenRAIL-M 有营收门槛、MinerU 有 MAU/营收附加条款）、**首次下载/离线部署**、**det 输入尺寸上限**，以及本项目特有的 **crates.io 版本落后 GitHub**。详见 §D。 |

### A.3 逐个拆解（重点：产品形态与 API 设计）

#### A.3.1 PaddleOCR HubServing（"老事实标准"）

- 形态：PaddleHub 插件式服务，一个模型一个服务进程；`ocr_system` = 检测 + 方向分类 + 识别串联。
- 部署：`hub install deploy/hubserving/ocr_system` → `hub serving start -m ocr_system`，默认端口 **8868**，`--port` 可改。
- **入参（易被误记，已实测纠正）**：`POST /predict/ocr_system`，`Content-Type: application/json`，body `{"images": ["<base64>", ...]}` —— **是 JSON + base64，不是表单文件上传**。证据：[test_hubserving.py L110-119](https://github.com/PaddlePaddle/PaddleOCR/blob/release/2.7/tools/test_hubserving.py)。
- **出参（被抄得最多的结构）**：
  ```json
  {"msg": "", "status": "0",
   "results": [[{"text":"...", "confidence":0.998, "text_region":[[x,y],...]}]]}
  ```
  - `status` 是**字符串** `"0"`（PaddleHub 全局约定，与 HTTP 状态码无关）；
  - `results` 是"每张图一层 list"的**二维**结构；
  - 行级字段 `text` / `confidence` / `text_region`；
  - `ocr_cls` 模块额外返回 `angle`。
  - 证据：[hubserving readme 第 4 节「返回结果格式说明」](https://github.com/PaddlePaddle/PaddleOCR/blob/release/2.7/deploy/hubserving/readme.md)、[module.py 的 `predict()`](https://github.com/PaddlePaddle/PaddleOCR/blob/release/2.7/deploy/hubserving/ocr_system/module.py)（返回 `{"text","confidence","text_region"}`）、[PaddleHub serving 文档](https://github.com/PaddlePaddle/PaddleHub/blob/develop/docs/docs_ch/tutorial/serving.md)（`{msg, results, status}` 信封）。
- 局限：PaddleOCR 3.x 主推 PaddleX serving，**main 分支已无 `deploy/hubserving` 目录**，仅 `release/2.7` 存在。新项目不应以它为唯一兼容目标，但**响应体值得兼容**。

#### A.3.2 PaddleX Serving（"当前官方主推"）

- 部署：`paddlex --install serving` → `paddlex --serve --pipeline OCR`，uvicorn 起在 `0.0.0.0:8080`；官方 Docker：`.../paddlex/hps:paddlex3.7-gpu` 与 `:paddlex3.7-cpu`（GPU 镜像要求 CUDA 11.8 驱动）。见 [PaddleX serving 文档](https://paddlepaddle.github.io/PaddleX/latest/en/pipeline_deploy/serving.html)。
- API：`POST /ocr`，body 为 JSON：
  - `file` 支持**服务器可访问的 URL** 或**文件 base64**；
  - `fileType`：0=PDF / 1=图片（含 TIFF，多页按页处理）；
  - 预处理开关直接进请求体：`useDocOrientationClassify` / `useDocUnwarping` / `useTextlineOrientation`；
  - `visualize` 控制是否返回可视化图。
- 响应：统一信封 `{logId, errorCode, errorMsg, result}`；`result.ocrResults` 是**按页**的数组（PDF 每页一个元素），每项含 `prunedResult`（精简后的 predict 输出）、`ocrImage`（标注框可视化图，base64 或预签名 URL）、`docPreprocessingImage`、`inputImage`。
- **四个值得直接抄的设计**：
  1. `logId` = 请求 UUID，贯穿日志与排障；
  2. 图像默认 base64 内联，可切 **「URL 返回模式」**（预签名）—— 直接解决"响应体过大"；
  3. PDF **默认只处理前 10 页**，需配置 `Serving.extra.max_num_input_imgs: null` 才解除 —— 有默认值且可解除，是正确的工程姿态；
  4. 失败响应 `errorCode` 与 HTTP 状态码对齐。
- 见 [通用 OCR 产线文档 · 服务化部署章节](https://github.com/PaddlePaddle/PaddleX/blob/develop/docs/pipeline_usage/tutorials/ocr_pipelines/OCR.md)。

#### A.3.3 RapidOCR / RapidOCRAPI

- **RapidOCR 本体是库**：把 PaddleOCR 模型转 ONNX，`pip install rapidocr onnxruntime`，一行 `RapidOCR()(img)`；推理引擎可换 `onnxruntime-gpu / tensorrt / openvino / paddle / pytorch / mnn`（Docker 按引擎分 `make build-onnxruntime-cpu` / `make build-tensorrt`）。见 [README](https://github.com/RapidAI/RapidOCR)。
- **RapidOCRAPI 是同社区另起的独立仓**（Apache-2.0），FastAPI + uvicorn，端口 **9003**：
  - `POST /ocr`，`multipart/form-data`，字段 `image_file`（文件）**或** `image_data`（base64 字符串），另有 `use_det/use_cls/use_rec` 布尔开关；
  - 响应是**以序号为 key 的扁平 dict**：`{"0": {"rec_txt": "...", "dt_boxes": [[x,y],...], "score": 0.99}, "1": {...}}`；无文本时返回 `{}`（**注意：空结果是空对象，不是空数组**）；
  - 硬限制：`MultiPartParser.max_part_size = 10MB`、`max_file_size = 20MB`；
  - **README 自认"没有考虑多进程处理并发请求，有需要请看 gunicorn"**。
  - 见 [main.py](https://github.com/RapidAI/RapidOCRAPI/blob/main/rapidocr_api/main.py)、[README](https://github.com/RapidAI/RapidOCRAPI)。
- **启示**：这是"库 → 服务"最常见的一步，但字段命名（`rec_txt/dt_boxes`）与 Paddle（`text/text_region`）、Umi（`text/box`）**三者全不一致** —— 字段名不统一正是本地 OCR 生态最大的集成痛点，也是我们可以用"兼容层"吃下的价值。

#### A.3.4 Umi-OCR（中文桌面事实标准，API 设计最"产品化"）

- 形态：Qt 桌面程序，Windows 7 x64 / Linux x64，**解压即用、完全离线**，内置 Rapid-OCR 引擎，另有 Paddle-OCR 引擎版（`scoop install extras/umi-ocr-paddle`），引擎以**插件**形式可换。
- HTTP：默认 `http://127.0.0.1:1224`。
  - `GET /api/ocr/get_options` —— **参数自省接口**：返回每个参数的类型/默认值/可选值/提示。例如 `ocr.limit_side_len` 枚举 `960/2880/4320/999999`，`ocr.cls` 布尔（纠正文本方向），`tbpu.parser` 枚举 **8 种排版解析方案**（`multi_para`/`multi_line`/`multi_none`/`single_para`/`single_line`/`single_none`/`single_code`/`none`）。**"服务端告诉客户端我能配什么"这个设计，对做 SDK/前端极其友好，建议直接借鉴。**
  - `POST /api/ocr`：body `{"base64": "...", "options": {...}}`（base64 **不带** `data:image/png;base64,` 前缀）→
    ```json
    {"code":100, "data":[{"text":"...","score":0.998,"box":[[x1,y1],[x2,y2],[x3,y3],[x4,y4]],"end":"\n"}], "time":0.32, "timestamp":...}
    ```
    - `code=100` 成功 / `101` 无文本 / 其余失败（失败时 `data` 是错误原因字符串）；
    - `data.format` 可切 `dict` / `text`（`text` 直接返回拼接好的纯文本）；
    - 行级 `end` 字段表示"该行结尾应接空格 / 换行 / 空"——**用 `本行文字 + 本行 end + 下一行文字…` 即可无损还原段落结构**，这是很聪明的设计；
    - `box` 是**顺时针四角** `[左上, 右上, 右下, 左下]`；
    - 返回 JSON 中非英文字符被转成 `\uXXXX`，且可能含转义换行 `\\n`（文档明确警告某些 HTTP 库会自动反转义导致解析失败）。
  - **文档（PDF）走异步任务**：`POST /api/doc/upload`（multipart：`file` + `json` 参数字符串）→ 返回任务 ID → 轮询 `/api/doc/result` → `/api/doc/download` → `/api/doc/clear`；支持 `pageRangeStart/pageRangeEnd/pageList` 指定页，可产出**双层可搜索 PDF**。
  - 见 [api_ocr.md](https://github.com/hiroi-sora/Umi-OCR/blob/main/docs/http/api_ocr.md) 与 [api_doc.md](https://github.com/hiroi-sora/Umi-OCR/blob/main/docs/http/api_doc.md)。
- 局限：需**先起 GUI 进程**（服务依附桌面端）；无 GPU；无并发/队列语义；Linux headless 非一等公民。

#### A.3.5 OCRmyPDF（PDF 后处理的事实标准）

- 形态：纯 CLI（+ Docker 多架构 x64/ARM），把已有 PDF 变成 **PDF/A 可搜索 PDF**，文字层精确压在图像下、不破坏原内容，**可处理数千页**，"Battle-tested on millions of PDFs"。
- 引擎：**只调 Tesseract**（4.1.1+，100+ 语言语言包；Windows 找不到 PATH 时查注册表），**纯 CPU，靠多核并行**（"Distributes work across all available CPU cores"）；**无 GPU 路径、无 HTTP API**。
- 输出：PDF/A（默认）、可去斜/清洁图像、保持原始嵌入图像分辨率、通常还能让文件变小。
- 许可：MPL-2.0（可商用、可闭源集成，但**修改 OCRmyPDF 自身源码需开源**）。
- 见 [README](https://github.com/ocrmypdf/OCRmyPDF)。
- **启示**：**"可搜索 PDF"是刚需输出格式**，但它与"在线 OCR 服务"是两个产品。我们的服务若要吃 PDF，必须明确是"输出文本/Markdown"还是"回写 PDF 文字层"—— 后者需要字体嵌入与坐标对齐，是独立工程量级。

#### A.3.6 Surya（VLM 化后的形态很值得学）

- 部署：`pip install surya-ocr`，**运行时自动拉起推理服务**：NVIDIA GPU 用 `vllm` Docker 容器（需 NVIDIA Container Toolkit），CPU/Apple Silicon 用 `llama-server`（llama.cpp，`brew install llama.cpp`）；可用 `SURYA_INFERENCE_URL=http://host:port/v1` 指向已有服务；`--keep_server` 复用已加载模型（否则每条命令都重付启动与加载成本）。
- 输出：Markdown / HTML；块坐标**归一化到 0–1000**；表格用 `data-cs`/`data-rs` 表达合并单元格、`data-kind="parent"`/`"ghost"` 标记跨行跨列；模型输出形如 `<|Text|><|120|><|87|><|881|><|255|><p>...</p>`；**自建服务必须返回 special tokens**（llama-server 要加 `--special`）。
- 吞吐调参：vLLM 侧 `--max-num-seqs` / `--max-num-batched-tokens`，客户端 `SURYA_INFERENCE_PARALLEL`；检测是 torch 模型，`DETECTOR_BATCH_SIZE` 控制显存。
- **许可（重要）**：代码 Apache-2.0，**权重是修改版 AI Pubs OpenRAIL-M：研究/个人/营收或融资 < 500 万美元的初创免费，超过需商业授权**。
- 见 [README · Inference backend prerequisites](https://github.com/datalab-to/surya)。
- **启示**：**"代码许可"与"权重许可"必须分开写进需求**；Surya 这种"CPU 走 llama.cpp / GPU 走 vLLM"的双栈，正是我们要避免的复杂度（两套运行时 = 两套坑 = 两套 bug）。

#### A.3.7 MinerU（文档解析服务化最完整）

- 部署：`pip install mineru[full]`（Python **3.11–3.14**）、Docker、`mineru server start`；默认安装即支持 Win/Linux/macOS CPU 推理，并对 **Intel/AMD/NVIDIA 独显与集显做 ONNX 自动加速**（自动探测设备、独显优先，集显按性能兼容性在 GPU/CPU 间选择），macOS 走 MPS/Metal；报称代表性核心推理约 **2–3× CPU 速度**。
- API：**两套并存**：
  - **异步任务** `/v1/tasks`（取代旧 `/v1/uploads`、`/v1/parse/jobs`）：file manifest、URL 输入、缓存上传复用、逐文件执行与下载、状态查询、取消 —— **破坏性变更**，客户端需同步升级；
  - **同步单文件**：独立 `file-parse-server` 的 `POST /v1/file_parse`，**只接受 multipart**，查询参数/未知字段/多文件/重复标量一律拒绝；参数：
    - `tier`：`flash`/`basic`/`standard`/`advanced`（仅影响 PDF/图片；省略时上游按 Standard→Basic→Flash→Advanced 选）
    - `ocr_mode`：`auto`/`txt`/`ocr`
    - `page_range`：如 `1-5`、`r1`、`all`
    - `output_formats`：`docx`/`html`/`latex`，**可重复**
    - `wait_timeout`：0–3600 秒
    - `request_id`：**提交前自存，断连后可恢复**
  - 见 [file_parse API](https://opendatalab.github.io/MinerU/usage/file_parse/)。
- **许可（重要）**：Apache-2.0 **+ 附加条款**：
  - MAU > **1 亿** 或月营收 > **2000 万美元** → 需单独商业授权；
  - **对外提供在线服务必须在界面或公开文档显著标注使用了 MinerU**，否则许可**自动终止**。
  - 见 [LICENSE.md](https://github.com/opendatalab/MinerU/blob/master/LICENSE.md)。

> **建议答案**：OpenAI 协议**无法表达行级 bbox 与置信度**，OCR 客户端恰恰需要结构化几何信息；因此主协议用自定义 JSON（对齐 Umi/Paddle 事实标准），同时提供 `/v1/chat/completions` 兼容层作为生态入口（让 Open WebUI、各类 SDK 能直接接入）。

#### A.3.9 顺带核实：docTR / Tesseract / EasyOCR 的"服务化缺位"

- **docTR**：库 + ghcr 镜像（`ghcr.io/mindee/doctr`），**官方无 HTTP 服务**；PyTorch / TensorFlow 双后端可选；Apache-2.0；现由 t2k GmbH 维护。
- **Tesseract**：CLI + `libtesseract` C/C++ API（`capi.h` / `baseapi.h`），**无 HTTP**；输出 txt/hOCR/ALTO/TSV/PDF；Apache-2.0；最新 **5.5.4（2026-10-28）**。"tesseract server" 只是社区 wrapper 的叫法，官方无此组件。
- **EasyOCR**：库，`Reader(..., gpu=False)` 可强制 CPU，仓库有 Dockerfile，**无 server**。
- **结论**：这三个都停在"库"，服务化全靠第三方 —— **"官方一等公民的本地 OCR 服务"确实是空位**。

### A.4 提炼：本地 OCR 服务的"事实标准"

**① 请求侧**

| 维度 | 事实标准 | 来源 |
|---|---|---|
| 传输 | 要么 `application/json` + base64，要么 `multipart/form-data` 文件；**两者都要支持** | PaddleX(JSON)、RapidOCRAPI(multipart)、Umi(base64) |
| 批量 | `images: [base64, ...]`（Paddle）或单文件单请求（其余）；`results` 按图分层 | PaddleOCR HubServing |
| 开关 | 把 `use_det/use_cls/use_rec`、`useDocOrientationClassify` 等**放进请求体**，不要只靠配置 | PaddleX、RapidOCRAPI |
| 自省 | `GET /api/ocr/get_options` 返回参数 schema（类型/默认值/枚举/提示） | Umi-OCR |
| 页码 | `page_range` / `pageList` / `max_num_input_imgs` | MinerU、Umi、PaddleX |
| 幂等/恢复 | `request_id` 客户端自存，断连后可查 | MinerU |

**② 响应侧（行级最小公约数）**

```
{ text, confidence|score, box|text_region, [end] }
```

四种方言对比：

| 方案 | 信封 | 行字段 | 坐标表示 |
|---|---|---|---|
| PaddleOCR HubServing | `{status:"0", msg:"", results:[[...]]}` | `text`, `confidence`, `text_region` | 4 点 `[[x,y],...]` |
| PaddleX | `{logId, errorCode:0, errorMsg:"Success", result:{ocrResults:[{prunedResult,...}]}}` | 见 `prunedResult` | 4 点 + 表格单元格坐标 |
| Umi-OCR | `{code:100, data:[...], time, timestamp}` | `text`, `score`, `box`, `end` | 4 点顺时针 `[左上,右上,右下,左下]` |
| RapidOCRAPI | **无信封**，顶层 `{"0":{...}}` | `rec_txt`, `dt_boxes`, `score` | 4 点 |

**③ 服务侧（工程语义）** —— 这些是"专业服务"与"demo 脚本"的分界线：

- `logId` / `request_id` 贯穿日志与断连恢复；
- PDF/多页 → **异步任务 + 轮询**（Umi 上传→轮询→下载；MinerU `/v1/tasks`），而非一个长连接；
- 大二进制（可视化图）→ **URL 返回模式**（预签名），而非全 base64；
- 页数上限有默认值且**可配置解除**（PaddleX 默认 10 页）；
- **并发语义**：RapidOCRAPI 明确"没考虑"、Umi 无队列 —— 这是空位（见 §A.5）。

**④ 输出格式矩阵（需求要明确取舍）**

| 格式 | 谁提供 | 我们是否该做 | 优先级 |
|---|---|---|---|
| 结构化 JSON（行 + 框 + 置信度） | 全部 | **必须**（主格式） | P0 |
| 纯文本 / 段落（含 `end` 语义） | Umi | **必须** | P0 |
| TSV / 词级框 | Tesseract、RustO!（`asTsv`/`asWords`） | 低成本，建议做 | P0 |
| Markdown（标题/表格/公式） | Surya、MinerU、olmOCR、PaddleOCR-VL | 需 layout 模型 | P1 |
| hOCR / ALTO | Tesseract 系 | 兼容既有 PDF 工具链 | P1 |
| **searchable PDF（双层）** | OCRmyPDF、Umi | 高价值差异化，工程量大 | P2 |
| DOCX | PaddleOCR-VL、MinerU | 企业交付常用 | P2 |

### A.5 从竞品提炼的「定位缝隙」

| 能力 | 谁做得最好 | 我们的取舍 |
|---|---|---|
| 同步单图 + 批量 | PaddleOCR HubServing | 必做（P0） |
| **异步任务 + 进度查询 + 断连恢复** | Umi-OCR、MinerU | 必做（P0）—— 本地批量场景的刚需，PaddleOCR 反而弱 |
| **并发/队列/背压/429 语义** | **全部缺失**（RapidOCRAPI 自认、Umi 无队列） | **差异化优势，做透（P0）** |
| **健康检查 / 指标 / 排障** | **普遍缺失** | **差异化优势（P0）**：`/healthz` 分离 liveness/readiness、Prometheus 指标 |
| 参数自省（tell me what I can set） | Umi-OCR | 借鉴（P0） |
| 多格式输出 | Tesseract（hOCR/ALTO/PDF）、MinerU（MD） | JSON/MD/TSV/spatial 必做；hOCR/ALTO P1；searchable PDF P2 |
| 模型自动下载 + 离线预置 | Surya/MinerU 自动；Paddle 手工 | 自动 + 强制离线 + bundle 导出（P0） |
| 版面/表格/阅读顺序 | MinerU、chandra、RustO 本身 | 上游已有，暴露即可（P0） |
| **单二进制零依赖** | Tesseract（依赖 leptonica）、RustO（纯 Rust） | **核心差异点** |

> **结论**：**「异步任务 + 完整可观测 + 单二进制零依赖」三者同时具备的方案几乎没有**。这是 FerroOCR 的产品缝隙 —— 应把这三条作为核心差异，**而不是去拼精度**。

### B.2 核心问题：Rust 里"同一套模型既能 CPU 又能 GPU"最务实怎么走

**结论：主路径 = 纯 Rust CPU（`rusto-nn` / `rten`）+ 可插拔 GPU（`wgpu` 优先、`cudarc` 次之）；`ort` 作为可选 feature 的"企业兼容逃生通道"，不做默认依赖。**

四条路径对比：

| 路径 | 做法 | 优点 | 缺点 | 成熟度 | 推荐度 |
|---|---|---|---|---|---|
| **P1 纯 Rust 自持** | ONNX/RTen 模型 + `rten`/`rusto-nn` 跑 CPU；`rusto-nn-webgpu` 跑 GPU（DX12/Vulkan/Metal 一套代码）；`rusto-nn-cuda` 给 N 卡服务器 | 单二进制、零 C++/OpenCV、体积小（RustO 自报 CLI **2.1 MB**）、许可干净、Win/Linux/mac 全覆盖 | GPU kernel 覆盖需自己扛；wgpu 表达算子有限（conv/gemm 定制 shader 工作量大）；**上游 GPU 后端目前只加速 GEMM/conv，覆盖度与性能无公开基准 —— 待实测** | 中（可用，需 spike） | ⭐⭐⭐⭐⭐ **与项目定位最一致** |
| **P2 ONNX Runtime 统一** | 全用 `ort`，CPU/GPU 靠 feature 切 EP：`cuda`/`tensorrt`/`directml`/`openvino`/`coreml` | 一套 ONNX 吃遍所有硬件；算子覆盖与性能是工业级；TensorRT/DirectML/OpenVINO 全部现成 | **引入 C++ 依赖**（`onnxruntime.dll`/`.so`），破坏"纯 Rust 零依赖"卖点；二进制膨胀；`ort` 仍是 2.0-rc；需处理 DLL 分发 | 高（工程最稳） | ⭐⭐ **仅作逃生舱** |
| **P3 统一 kernel 层** | `burn` + `cubecl` 写模型，后端切 `cpu/cuda/rocm/metal/vulkan/wgpu` | 代码写一遍，**ROCm/Metal 都覆盖** | 需把 Paddle 模型**重写成 burn 图**（或 burn-import），迁移成本高；算子/精度对齐要验证 | 中低（长期最优） | ⭐⭐⭐ 二期评估 |
| **P4 tch / candle 直接吃权重** | 吃 PyTorch/safetensors | 上手最快（deepseek-ocr.rs 就是这么干的） | libtorch/CUDA 工具链重、分发痛苦；candle 无 ROCm；OCR 的 DBNet/CTC 迁移成本高 | — | ⭐ 不推荐 |

**推荐：同时保留 P1 的三条腿（CPU/wgpu/CUDA），用 feature 门控。**

```toml
[features]
default  = ["cpu"]                        # 纯 Rust，无外部运行时
cpu      = ["rten"]                       # 或 rusto-nn
gpu-wgpu = ["rusto-nn-webgpu"]            # Win(DX12/Vulkan) / Linux(Vulkan) / macOS(Metal) 一套代码
gpu-cuda = ["rusto-nn-cuda"]              # NVIDIA，动态加载 nvcuda.dll/libcuda.so，缺失自动回落 CPU
onnx-cpu = ["ort"]                        # 逃生通道：企业已有 ONNX 资产
onnx-gpu = ["ort/cuda", "ort/tensorrt"]   # 服务器高吞吐
onnx-dml = ["ort/directml"]               # Windows A/N/Intel 通吃（无 CUDA 环境）
```

> **一条铁律**：GPU feature 必须是**运行时可选**（动态加载），不能是编译期唯一路径。`rusto-nn-cuda` 的"检测不到 `nvcuda.dll` 就回落纯 Rust CPU"正是正确姿势 —— 这让"同一个安装包在任何机器上都能跑"成立，也避免了"用户装了 CUDA 版但机器没驱动 → 直接崩"这类最恶心的线上问题。

### B.3 平台差异（决定的不是代码，是发行物数量与 SLA）

| 平台 | CPU | GPU 首选路径 | 不可用 | 分发注意 |
|---|---|---|---|---|
| **Windows + NVIDIA** | AVX2 / AVX-512 | ① **CUDA**（`cudarc`，需驱动，**不需要装 CUDA Toolkit**，动态加载）② DirectML（`ort/directml`，DX12）③ Vulkan（`wgpu`） | Metal | 单 exe + 可选 `onnxruntime.dll`；CUDA 版无需捆绑 SDK；驱动版本碎片化是主要坑 |
| **Windows + AMD/Intel** | AVX2 | **DirectML**（`ort`）/ Vulkan（`wgpu`） | CUDA | 无 CUDA 路径；DirectML 是 AMD 上唯一"官方级"路径 |
| **Linux + NVIDIA（服务器）** | AVX-512 | **CUDA**（`cudarc` 或 `ort/cuda`）、**TensorRT**（`ort/tensorrt`，最高吞吐） | — | 容器需 `--gpus all` 暴露 `libcuda.so.1`，**无需** CUDA toolkit；推荐出 `-cuda` 与 `-cpu` 两个镜像 tag（PaddleX 即如此） |
| **macOS（Apple Silicon）** | NEON | **Metal**（`wgpu` 的 `metal` / `candle` 的 `metal` / `burn` 的 `metal`） | **CUDA 永远不可用**；无 NVIDIA | Universal 或分 arm64/x86_64；Metal 无 FP64，注意精度；`tch` 需 libtorch |
| **Linux + AMD** | AVX2 | ROCm：`ort/rocm`、`ort/migraphx`、`burn` 的 `rocm`；`wgpu` 走 Vulkan | `cudarc` | **Rust 侧 ROCm 支持最弱**（candle 无 ROCm）；需求里应写"实验性/待验证" |
| **浏览器 / WASM** | SIMD128 | WebGPU（`navigator.gpu`） | 全部原生 | RustO 上游 `rusto-wasm` 已支持 |
| **Linux ARM / 国产化** | NEON | `ort/cann`（昇腾）、`ort/vitis`、`ort/rknpu`、`ort/qnn`、`openvino` | 多数 | 只承诺 CPU（NEON）；其他后端写"社区驱动" |

> **一句话**：**macOS 只能 Metal，Windows 首选 DirectML/Vulkan，Linux 服务器才值得上 CUDA/TensorRT** —— 所以"GPU 支持"在需求里必须**按平台分别写 SLA**，不能一句"支持 GPU"糊过去。

### B.4 模型格式 ↔ 后端绑定关系（选格式 = 选后端）

| 模型格式 | 能吃它的 Rust 引擎 | 能否 GPU | 备注 |
|---|---|---|---|
| **ONNX** | `ort`（全 EP）、`tract`（CPU）、`rten`（CPU）+ **`rusto-nn` 自带 loader** | ort 可；tract/rten 库**不可**；**`rusto-nn` 取决于后端算子覆盖** | **最通用**；PaddleOCR → ONNX 有成熟路径（RapidOCR 就干这个） |
| **RTen (.rten)** | `rten` / `rusto-rten`（**CPU-only**）+ **`rusto-nn` 的 `load_rten`** | ⚠️ **见 §B.4 更正** | RustO 0.4 默认模型即 `.rten`（`det.rten`/`rec.rten`/`indra_order.rten`） |
| **MNN** | `rusto-mnn`（C++ FFI）+ **`rusto-nn` 的 `load_mnn`（纯 Rust）** | 经 `rusto-nn-cuda`/`-webgpu`（但仅 GEMM） | 原生 C++ MNN 支持 OpenCL/Vulkan/CUDA；Rust 移植版受 `DeviceBackend` 覆盖度限制 |
| **safetensors / PyTorch** | `candle`、`burn`、`tch` | candle: CUDA/Metal；burn: 全后端 | 适合 VLM（dots/olmOCR/PaddleOCR-VL 那类） |
| **GGUF** | 只能靠 `llama.cpp` 外部进程（Surya 的 CPU 路线） | Metal/CUDA via llama.cpp | 非 Rust 原生，需 sidecar 进程 |

> ### ⚠️ 更正（2026-11-10 复核，推翻本节初稿结论）
>
> 初稿写「`.rten` 是 CPU-only 格式 → GPU 档位必须配套 `.onnx`」——**这个结论不成立**，它混淆了两个层次：
>
> 1. **rten 引擎**（`robertknight/rten`）确实明示 "CPU inference only"。但这句只约束**用 rten 引擎执行**的场景，即 `rusto-rten` 后端——而该后端已被上游 benchmark 证明极慢（OmniDocBench 12.0 s vs 默认 1.8 s），本项目**默认不用它**。
> 2. **`rusto-nn` 的执行路径与模型格式无关**：`crates/rusto-nn/src/graph/loader/` 下并列三个 loader —— `mnn.rs`（25 KB）、`onnx.rs`（40 KB）、`rten.rs`（42 KB），全部产出同一个 `Graph` IR（`loader/mod.rs`：`pub use {load_mnn, load_onnx, load_rten}`）；执行统一走 `graph/mod.rs` 的 `execute_node`（2403 行），内部调 `kernels::conv::conv2d`、`kernels::depthwise::depthwise_conv2d_nchw`、`kernels::gemm::gemm`。
> 3. **因此**：`.rten` / `.mnn` / `.onnx` 在 `rusto-nn` 下是**等价输入**，GPU 能用与否只取决于 `DeviceBackend` 是否覆盖该算子（当前仅 `gemm`），**与文件后缀无关**。默认的 `.rten` 模型同样能走 GPU 后端，只是照样只有 GEMM 下沉。
>
> **修正后的需求结论**：模型格式**不构成 GPU 的支持边界**，不必为此维护两套资产；判断 GPU 收益要看**算子覆盖**（PRD §9.4），不是扩展名。三种格式都保留支持即可。

## D. OCR 服务的常见需求陷阱（需求文档风险输入）

**格式：陷阱 → 现象/证据 → 需求上该怎么约束。**

| # | 陷阱 | 现象与证据 | 需求约束（可直接抄进 PRD） |
|---|---|---|---|
| **D1** | **EXIF 方向未处理** | 手机拍摄图常带 EXIF Orientation，直接解码得到"躺着"的图，检测框全错、识别率骤降。Umi 提供 `ocr.cls`「纠正文本方向」；PaddleX 有 `useDocOrientationClassify` / `useTextlineOrientation` | **解码阶段先应用 EXIF 再送模型**（P0）；方向分类（0/90/180/270）作为**默认开启但可关**的独立阶段；响应回传 `appliedRotation` 让调用方可核对；提供 `exif_policy: auto / ignore / rotate:N` |
| **D2** | **低质量扫描件 / 倾斜 / 折痕 / 透视** | 噪点、摩尔纹、装订阴影让 det 失效。RustO 内置 **3D UVDoc 去扭曲**（`withAutoUnwarp`）；PaddleX 有 `useDocUnwarping` | 去扭曲/去噪作为**可选预处理阶段**（**默认关**，开启会增加 30%+ 延迟），按质量启发式触发；验收集必须含 ≥200 dpi 扫描件与手机翻拍两类 |
| **D3** | **手写体** | PP-OCR 系手写能力弱；只有 VLM（PaddleOCR-VL / dots.ocr / olmOCR / chandra）才宣称支持手写 | **明确"不承诺手写"**，写清能力边界；若必须支持，走 VLM 后端并单独标注硬件门槛（≥8–12 GB 显存），不进通用 SLA |
| **D4** | **表格结构** | 表格（合并单元格）无法用"行 + 框"表达；Surya 用 `data-cs`/`data-rs` 专有属性，PaddleX 给单元格坐标，Umi 完全不做；上游 `table.rs` 为实验态、schema 不稳 | 一期**只做"表格内文字按行输出"，不做单元格重建**；标记 `experimental`，`tables` 字段**允许缺失**；二期若做，响应新增 `table: {rows, cols, cells[]}` 并单列验收指标（TEDS） |
| **D5** | **多栏 / 阅读顺序** | 双栏论文按坐标 y 排序会串行。Umi 用 `tbpu.parser` **8 种方案**；RustO 有 `withLayoutReading`（PicoDet 版面分类 + 神经阅读序，上游数据 57% → 64%） | 阅读顺序必须是**独立可配模块**（默认 `multi_para`），提供 `readingOrder: "natural" \| "raw"` 两档；**返回结果既给已排序序列，也保留原始 `box`**，让调用方可自行重排 |
| **D6** | **公式** | PP-OCR 只出散字符；公式需 VLM 才能出 LaTeX | **公式 = 二期能力**，且必须以 `formula: [{box, latex}]` **独立字段**返回，不混入正文 text；一期文档显式声明"公式降级为普通文本" |
| **D7** | **竖排中文（含从右到左）** | Umi 文档明确"竖排需 OCR 引擎本身支持"；PP-OCR 竖排支持有限 | **竖排 = 明确的能力等级**（"支持识别，阅读顺序按列自右向左"），验收集加入古籍/竖排样本；**不可默认承诺** |
| **D8** | **印章 / 水印 / 票据叠字** | 红章覆盖文字是中文票据经典难点；PaddleOCR-VL 宣称在印章上增强 | 印章 = **"尽力而为，不做 SLA"**；票据场景需单独的**忽略区域**（Umi 的「忽略区域」排掉水印文字）与颜色通道分离预处理 |
| **D9** | **PDF 多页 + 并发** | PaddleX **默认只处理前 10 页**；Umi 走上传→轮询→下载任务流；MinerU 用 `/v1/tasks` | ① `page_range` 必须可指定，**默认上限显式声明**（建议 100 页）并可配置解除；② 多页必须走**异步任务 + 任务 ID + 断连可恢复**（对齐 MinerU 的 `request_id`）；③ 并发粒度定义为**页级**而非文档级；④ **逐页流式处理，禁止整册载入内存** |
| **D10** | **大图切分（det 输入尺寸上限）** | 检测模型有固定输入边长：PaddleOCR `det_limit_side_len=960`；Umi 枚举 960/2880/4320/999999。超长图整图 resize 会丢小字 | 文档**公开 `det_limit_side_len` 默认值与可调范围**；实现**自适应切分 + 重叠带合并**；响应必须带 `scale` 并**保证框能映射回原图坐标**（**最容易漏的 P0 验收项**） |
| **D11** | **长宽比极端（长截图、票据）** | 1080×20000 的长截图等比缩放后文字变 1–2 px，直接不可识别 | **按长宽比分支策略**（如 ratio > 8 时沿长边切片，单片不超过 N 像素），切片边界**必须有重叠**以恢复跨片文本行；提供 `split_extreme_ratio` 开关 |
| **D12** | **内存 / 显存 OOM** | 并发多图 + 大模型 + 可视化图（PaddleX 的 `ocrImage` base64）极易 OOM；Surya 需调 `DETECTOR_BATCH_SIZE` 控 VRAM | ① **显式并发上限 + 队列 + 背压**（不是"支持并发"这种空话），超限返回 **429 + `Retry-After`**；② 可视化图**默认不返回**（对齐 PaddleX"默认不返回图像"），需要时走 URL 模式；③ 请求级 `max_pixels` 上限，超限 **413** 而非 OOM；④ 引擎池 + 单请求 panic 隔离 |
| **D13** | **模型首次下载 / 离线部署** | RustO 首次运行自动从 HF（`byrizki/rusto-models`）下载；PaddleX/olmOCR/MinerU 都要拉权重。**企业内网无外网时启动即失败** | ① **首次下载必须可禁用**（`--offline` / `FERRO_OFFLINE=1`），缺模型时给**明确错误码 + 下载命令**，而不是阻塞；② `ferroocr models pull/verify/bundle` + SHA-256 校验；③ 镜像分 `-slim`（无模型）与完整版；④ 缓存目录可环境变量覆盖 |
| **D14** | **CPU 上"大模型 vs 小模型"权衡** | RustO 档位：Indra ~5.5 MB / PP-OCRv6 Tiny ~6 MB（INT8 3.4 MB）/ Small ~30 MB（16.2 MB）/ Medium ~134 MB（75.7 MB）—— **体积差 20 倍以上**，CPU 延迟差数倍。用户以为换 medium 就更好，结果慢 5× | 提供 **`tier` 语义化档位**（`fast` / `balanced` / `accurate`，或 `tiny/small/medium`），**每档标称 CPU 单页 P50/P95 延迟 + 内存占用 + 精度**；默认 `balanced`；**禁止"一个模型打天下"** |
| **D15** | **许可证：代码 ≠ 模型** | 详见 §E | 详见 §E：**建立三列许可表**、**权重不进镜像/crate、运行时下载 + 校验** |
| **D16** | **crates.io 版本落后 GitHub（本项目特有）** | `rusto-rs` GitHub 已发 **v0.4.0（2026-11-10）**，但 **crates.io 仅 0.3.2（2026-10-25）**；README 里 0.4.0 的 fluent builder / Indra 默认模型 / 6 阶段流水线，下游 `cargo add` **根本拿不到** | **锁定 git 依赖或 vendor 化**（`rusto-rs = { git = "...", tag = "v0.4.0" }`）；**禁止在需求/文档中引用未发布到 crates.io 的 API**；把"上游发版节奏"列为外部依赖风险，**预留 fork 维护预算** |
| **D17** | **GPU 后端"名义支持 ≠ 实际可用"** | `rusto-nn-cuda` 自称动态加载、缺失回落；`deepseek-ocr.rs` 的 CUDA 明确标注 **alpha**；`vulkano` 一年多未发版；`rten` 明示 CPU-only；Rust 侧 ROCm 最弱 | **每个后端必须有"成熟度标签"**（stable / beta / experimental）并在 `ferroocr devices` / `ferroocr info` 里暴露；**GPU 只对 stable 后端承诺性能 SLA**，其余仅承诺"能跑"；把"GPU 是否更快"做成**可测结论 + CI 门禁** |
| **D18** | **并发语义与状态** | RapidOCRAPI README 直言"未考虑多进程并发"；Umi 服务依附 GUI 进程，无队列 | 明确**进程内并发模型**（`tokio` + 有界 `Semaphore` + 请求级超时 + 背压）；定义**优雅关闭**（在途请求 drain）；`/healthz` 区分 **liveness / readiness**（readiness 必须反映模型是否已加载完成）；明确 429/503 语义 |
| **D19** | **精度不可复现 / 上游 benchmark 归属误引** | 升级后结果变化会影响下游业务；上游 README 把 OmniDocBench 归给 `datalab-to`，实际官方仓在 `opendatalab` | **输出契约版本化** + **精度门禁 CI**（固定验收集、固定阈值，回归即挂）；宣传材料引用第三方 benchmark 前必须核对**官方仓库归属与版本**，标明"数据来自 X，版本 Y，我们未独立复现" |
| **D20** | **结果体积过大** | 大量 polygon 可让 JSON 到数十 MB | 默认裁剪坐标精度（保留 1 位小数）；支持 gzip/zstd；`include_polygon=false` 只给矩形框；**大响应走 URL 模式** |

## F. 尚未核实 / 待确认清单（**不要当结论用**）

1. **Docker Hub 占用**：本次 `hub.docker.com` 全部超时（curl 000），`ferroocr` 等名字是否被占 —— **未验证**。上线前需手动 `docker pull` 试拉或用 API 复查。
2. **`.dev` 域名**：`rdap.nic.google` 不可达，所有 `.dev` 状态 —— **未验证**（`.com` 已用 Verisign RDAP 实测）。
3. **PaddleOCR 模型文件（PP-OCRv6 / PaddleOCR-VL）的具体许可条款**：项目整体 Apache-2.0，但模型卡未逐一抓取（HF API 本次不可达）—— **待确认**，商用前必须逐个模型卡核实。
4. **`rusto-nn-webgpu` / `rusto-nn-cuda` 的实际性能与算子覆盖**：无公开 benchmark，仅有 README 宣称 —— **待实测**。建议立项第一个 spike 就是"同一张 1600×993 图上 CPU vs wgpu vs CUDA 的 det+rec 耗时与内存"。
5. **RustO 0.4.0 是否提供 HTTP server**：仓库树（1177 个路径）中未见 `server`/`http`/`api` crate，仅 `rusto-node`、`rusto-wasm`、CLI —— 大概率**没有**，我们做服务层正是补这个空位；若上游后续加，需重新评估差异化。
6. **PaddleOCR 3.x 是否仍维护 HubServing**：main 分支已无 `deploy/hubserving`，仅 `release/2.7` 存在 —— 我们要兼容的是它的**协议**，不是它的实现。
7. **`ort` 2.0 正式版时间表**：目前 max_stable 为 None，仅 rc.15 —— 若我们把它当逃生通道，需评估 rc → stable 的破坏性变更风险。

## G. 给 PRD 的三条结论

1. **产品缝隙明确**：市面上的本地 OCR 服务，**「单二进制零依赖 + 异步任务 + 完整可观测 + 真并发语义」四者兼具的基本没有**。FerroOCR 应把这几条作为核心差异，**而不是去拼精度**（精度拼不过 PaddleOCR-VL / dots.ocr 这类 VLM，且不该拼）。
2. **GPU 必须"诚实"**：`wgpu` 覆盖通用 GPU、`cudarc` 覆盖 N 卡；但上游后端目前只加速 GEMM，**必须把"GPU 是否更快"做成可测结论 + CI 门禁**，并在文档中如实标注 **capability matrix（平台 × 后端 × 成熟度）**。注意区分：**rten 引擎**是 CPU-only（本项目不用），但 **`.rten` 模型格式经 `rusto-nn` 的 `load_rten` 转 IR 后同样能走 GPU 后端**——格式不是 GPU 的边界，算子覆盖才是（详见 §B.4 更正）。
3. **合规上管住模型分发**：**权重运行时下载 + SHA-256 校验 + 三列许可表**，是成本最低、风险最小的做法；Surya/MinerU 的附加条款必须让法务过一遍。
