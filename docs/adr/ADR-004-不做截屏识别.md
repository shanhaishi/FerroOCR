# ADR-004 · 不做截屏 / 屏幕区域识别

| 项 | 内容 |
|---|---|
| 状态 | **已采纳**（2026-11-11） |
| 影响范围 | PRD §3.2 非目标 N11、§5.2.1 参数表（不提供 `--screen`）、§10 风险 R12 |

## 背景

「OCR 工具」的常见附加能力是直接框选屏幕一块区域然后识别，省掉用户先截图再传文件的步骤。这项能力曾被列为待确认项（PRD 早期版本的 Q11）：做，还是不做？

## 决定

**不做。** FerroOCR 只接受调用方传入的图片（路径或字节），不提供任何截屏、屏幕区域选择、热键触发的入口。

## 理由

1. **调用方本来就有更好的截屏 API。** 按键精灵有 `Plugin.Screen` / `GetCursorPos`，Python 有 `PIL.ImageGrab`，aardio 有 `mouse.screen`。这些 API 在调用方自己的进程里，**比我们更清楚要截哪块屏**——它们知道用户刚点了哪里、当前是哪个窗口、业务上下文是什么。我们从外部猜，只会猜错。
2. **截屏的工程成本被低估。** 多显示器、DPI 缩放（125% / 150% / 每屏不同）、窗口遮挡、最小化、权限与会话隔离、远程桌面场景——每一项都要单独处理，且都要在有对应硬件配置的机器上验证。
3. **它会改变本项目的性质。** 一个"接收图片、返回文字"的组件是被动的、可预测的；一个"监听热键、抓取屏幕"的进程是主动监控。后者会显著扩大杀软启发式扫描的命中面，与既有风险 R12（自解压 + 常驻行为易被误报）叠加。

## 后果

- PRD 的非目标清单新增 N11，并写明理由，避免日后被重新提议时重复讨论。
- 参数表里不出现 `--screen` 之类的入口；若将来要加，它属于**新的一类产品**，应当独立立项。
- 调用方的接入示例里不出现截屏代码——示例只演示「传入图片路径」这一件事。

## 教训

**「顺带做一个」听起来便宜的能力，往往是把产品从被动变成主动的那一步。** 判断要不要做，主要看它会不会改变组件与调用方之间的责任边界，而不是看实现它需要多少行代码。
