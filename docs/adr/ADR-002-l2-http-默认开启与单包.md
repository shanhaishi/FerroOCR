# ADR-002 · L2 HTTP 默认开启，且只出一个包

| 项 | 内容 |
|---|---|
| 状态 | **已采纳**（2026-11-11） |
| 影响范围 | PRD §5.2.1 启动参数表、§5.3.1 阶梯默认值、§5.10 安全、§9 验收 A19–A22 |
| 关联 | [ADR-001](ADR-001-传输层四级接入阶梯.md) |

## 背景

[ADR-001](ADR-001-传输层四级接入阶梯.md) 定了四级阶梯之后，还剩两个判断题：

1. **L2（本地 HTTP）默认开还是关？** 当时定的是默认关，理由是「不暴露网络面更安全」，需要显式 `--http` 才启用。
2. **要不要出两个包？** 为了绕开上面的争议，曾提议发两个二进制：`ferroocr.exe`（默认关）与 `ferroocr-tool.exe`（默认开 L2，专供老工具）。

## 决定

**两个都否掉，改为：只出一个 `ferroocr.exe`，L2 默认开启，行为差异全部用启动参数表达。**

## 为什么

### 默认关站不住脚

- 端口**只绑 `127.0.0.1`**，此时「不暴露网络」这条理由根本不成立——外部主机连不上一个回环地址。
- 默认关会逼着每个调用方学会传 `--http`。而**老工具的使用者恰恰是最不可能去传参数的那批人**：他们拿到的是一个要双击的 exe，不是一份命令行文档。
- 「默认开 + 一道回环限制」比「默认关 + 要求每个调用方都会传参」更接近 P1（附属工具，零配置）。

关掉的口子仍然保留：`--no-http` 一键关闭；`--bind` 传非回环地址直接拒绝启动。

### 双包破坏 P3

「产物尽可能少」是本项目的第三条定位。两个 exe 意味着构建产物翻倍、分发时要向使用者解释该下哪一个、版本要各自对齐、bug 要复现两遍。**而它解决的只是一个默认值问题，那是启动参数该干的事。**

用户的实际经验也支持这个判断：市面上同类工具通常优先用 HTTP 交互，默认开才是符合预期的姿态。

## 落地方式

| 项 | 做法 |
|---|---|
| 发行物 | 唯一 `ferroocr.exe`，CPU 引擎 + GPU 引擎（ORT + DirectML）+ 模型全在内，≤60 MB |
| 默认姿态 | 无参数 = 常驻 + L2 开 + L3 开 |
| 参数表 | PRD §5.2.1：`--no-http` / `--http` / `--port` / `--bind` / `--pipe` / `--idle` / `--device` / `--pool` / `--max-ram` / `--log` / `--wait` / `--once` / `--selftest` / `--version` / `--help` |
| 优先级 | 命令行 > 环境变量 > `endpoint.json` > 内置默认 |
| 逃生口 | `FERRO_ARGS` 环境变量，SDK 拉起进程时原样附加——调用方改不了代码也能统一改服务行为 |
| 自省 | `--help` 与 `GET /info` 必须回显**生效值 + 来源**（哪个来源定的） |

## 后果

- 验收标准新增「只放一个 exe、双击不带参数，HTTP 立即可连」，这是整个项目最核心的一条可用性验收。
- `.gitignore` 与发布流程只需管一个产物。
- 安全模型从"默认关闭"变为"默认回环 + 可选 token"，因此 PRD §5.10 增加了对 `Origin` / `Host` 的校验（防 DNS rebinding）与可选的 `FERRO_HTTP_TOKEN`。

## 教训

**标成「可选 / 默认关闭」的功能，如果只有"不方便的人"才用，那它就是必需品。** 默认值本身是一条产品决策，不是一个配置项——把它推给用户，等于把设计责任转嫁给了最没有能力承担的人。
