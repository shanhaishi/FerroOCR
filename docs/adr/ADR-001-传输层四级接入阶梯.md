# ADR-001 · 传输层：从 Named Pipe 单通道改为四级接入阶梯

| 项 | 内容 |
|---|---|
| 状态 | **已采纳**（2026-11-11），未废弃 |
| 影响范围 | PRD §5.3 全部传输需求、§5.5 SDK 范围、§9 验收 A15–A22 |
| 取代 | 更早的「Named Pipe 作为唯一主通道」设计 |

## 背景

FerroOCR 的定位是**附属工具**：它自己不是产品，而是被别的程序调用的 OCR 能力。这条定位意味着一个硬约束——**能接入哪种传输方式，不是由我们选的，是由最弱的那个调用方决定的**。

目标调用方清单里包含按键精灵、易语言、aardio 这类技术栈很老的脚本工具。它们的使用者通常不会为了一次 OCR 去装运行库、改配置、或写复杂的调用代码。

## 最初的决定（已废弃）

最初把 **Windows Named Pipe**（`\\.\pipe\ferroocr-v1`，NDJSON 单行 JSON 帧）定为唯一主通道，理由是：无端口、无防火墙弹窗、无网络暴露、天然支持多客户端、有 Windows 原生的权限控制。HTTP 只作为「可选编译、默认不启用」的备用通道。

## 为什么废弃

两条硬事实推翻了上述假设：

1. **按键精灵连不了 Named Pipe。** 从脚本调命名管道要过 `CreateFile` / `ReadFile`，还要处理 `OVERLAPPED` 异步结构。按键精灵的 `Declare Function` 只能声明 `GetAsyncKeyState` 这类简单签名，做不到带 `SECURITY_ATTRIBUTES` / `OVERLAPPED` 的管道客户端。社区里按键精灵调 OCR 的通行做法是 `CreateObject("MSXML2.XMLHTTP")` 发 HTTP POST，或用第三方 DLL 插件——而插件必须放进按键精灵的 `plugin` 目录并**重启软件**才能被识别，等于要求最终用户额外安装，直接违反 P1。
2. **「静默拉起常驻进程」这个设计本身也预设了调用方能力。** 老工具最多能 `RunApp` 一条命令然后等文件出现，既拿不到子进程的 stdout，也连不上管道。

更根本的问题是**判断顺序错了**：先选了一种「技术上更优雅」的传输方式，再假设所有调用方都能适配它。正确的顺序是反过来——从调用方的最小能力出发，倒推传输方式。

## 决定

改为**四级接入阶梯**，四级共用同一套 JSON schema 与同一套错误码，换级不需要改业务代码：

| 级别 | 方式 | 需常驻 | 延迟量级 | 面向的最弱调用方 |
|---|---|---|---|---|
| **L0** | `ferroocr.exe ocr --image a.png --out r.json` | ❌ | ~1–2 s | 只会 `RunApp` + 读文件 |
| **L1** | 命令 + 文件（`--in req.json --out res.json`） | ❌ | ~1–2 s | 拿不到子进程 stdout |
| **L2** | 本地 HTTP `127.0.0.1:1224` | ✅ | ~5–15 ms | 只会 `CreateObject("MSXML2.XMLHTTP")` |
| **L3** | Named Pipe `\\.\pipe\ferroocr-v1` | ✅ | ~1–3 ms | 有 SDK 的现代语言 |

Named Pipe 并未被否定——它仍是 L3，仍是 SDK 的默认路径、仍是延迟最低的一条。改变的是：**不再假设所有人都能用它**。SDK 按 L3 → L2 → L0 自动降级。

## 后果

- PRD 新增 §5.3.1 阶梯表；验收标准里加入「按键精灵走 L2」「按键精灵走 L0」「端口占用顺延」「未开 L2 时连接被拒」四条实测项。
- 接口的复杂度从「一条快路径」变成「四条路径 + 一个统一 schema」，实现成本上升，但这部分成本换掉的是**可达性**，不可省。
- 由此衍生出两个后续决策：[ADR-002](ADR-002-l2-http-默认开启与单包.md)（L2 默认开启）、以及 SDK 范围收紧（老工具一律不写 SDK）。

## 教训

1. **「调用方支持什么」必须先问清，再定传输层。** 写下主通道设计时没有核实过任何一个真实调用方的技术栈，这是需求调研的缺口，不是编码问题。
2. **对附属工具而言，可达性优先于优雅。** 端口、防火墙弹窗这类"设计者眼里的不干净"，是设计者的洁癖，不是用户的成本。
