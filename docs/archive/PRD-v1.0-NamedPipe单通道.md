# PRD v1.0 存档 · Named Pipe 单通道版（已废弃）

> **状态：已废弃（2026-11-11 晚，v1.0 发布数小时内）**
> 本文不是 v1.0 的逐字副本（v1.0 被 **原地改写** 为 v1.1，无独立快照）。这里记录 **v1.0 的传输层设计 + 它为什么错**，供追溯决策。
> 现行版本：[PRD v1.1](../PRD-FerroOCR.md)

---

## v1.0 的传输层设计

| 项 | 内容 |
|---|---|
| 主通道 | Windows Named Pipe `\\.\pipe\ferroocr-v1`，NDJSON 单行 JSON 帧 |
| 备用通道 | localhost HTTP —— **"可选编译，默认不启用"**（F-3.2） |
| 一次性模式 | 仅 `ferroocr.exe <图片路径>`，结果输出到 **stdout** |
| SDK | 五套（Python / C# / Node / Go / Rust），**全部只走管道** |
| 常驻 | SDK 首次调用时 `CreateProcess(DETACHED_PROCESS)` 静默拉起 |

v1.0 的原文表述（PRD §5.3 F-3.1）：

> **主通道：Windows Named Pipe**。优点：无端口、无防火墙弹窗、无网络暴露、天然支持多客户端、Windows 原生权限控制。

F-3.2 对 HTTP 的判断：

> **备用通道：localhost HTTP**（可选编译，默认不启用）。仅当某些语言/工具集成命名管道极不方便时才提供。**默认关闭**，启用需显式开关。

## 它为什么错

业务方指出（2026-11-11，PRD 修订的直接触发）：

> 「我要用的编程语言可能涉及到很古早或者技术栈落后的（例如按键精灵）」

**两条硬事实推翻了 v1.0 的核心假设：**

1. **按键精灵连不了 Named Pipe。** Windows 命名管道要从脚本调 `CreateFile` / `ReadFile`，还得处理 `OVERLAPPED` 异步结构。按键精灵的 `Declare Function` 只能声明简单签名，能调 `GetAsyncKeyState` 这类，**做不到带 `SECURITY_ATTRIBUTES`、`OVERLAPPED` 结构的管道客户端**。社区里按键精灵调 OCR 的实际做法是 `CreateObject("MSXML2.XMLHTTP")` 发 HTTP，或由第三方封装 `*.dll` 插件（需装进按键精灵 `plugin` 目录并重启，等于要求用户做额外安装——违反 P1）。

2. **"静默拉起常驻进程"这个设计本身也依赖调用方能启动进程并连管道。** 老工具最多能 `RunApp` 一条命令然后等文件出现，它拿不到子进程 stdout，也连不上管道。

**更根本的错误是判断顺序**：v1.0 先选了"技术上更优雅"的传输方式（无端口、低延迟），再假设调用方都能适配它。而 P1 要求的是**反过来**——从调用方的最小能力出发，倒推传输方式。**最弱调用方决定下限**：连 `MSXML2.XMLHTTP` 都没有的环境，还得能用一个命令 + 一个文件跑通。

## v1.1 的修正

把单一主通道改为 **四级接入阶梯**（[§5.3.1](../PRD-FerroOCR.md#531-四级接入阶梯本版核心修正)）：

| 级别 | 方式 | 需常驻 | 最弱调用方 |
|---|---|---|---|
| L0 | 一次性进程，结果写文件 | ❌ | 只会 `RunApp` |
| L1 | 请求/结果走文件 | ❌ | 拿不到 stdout |
| L2 | 本地 HTTP `127.0.0.1` | ✅ | 只会 `CreateObject("MSXML2.XMLHTTP")` |
| L3 | Named Pipe | ✅ | 有 SDK 的现代语言 |

**保留 v1.0 的全部优点**（L3 仍是 SDK 默认、仍然是延迟最低的路径），只是不再假设所有人都能用它。

## 保留下来、仍然正确的部分

v1.0 的这些决策未被推翻，v1.1 继续沿用：

- **JSON 单一 schema**：现在扩展为"四级结构完全一致"，反而更有价值
- **路径直传**（`image_path` 而非 base64）：对老工具尤其重要，传路径比传 base64 容易得多
- **模型内置进 exe**：L0 一次性模式完全依赖它——外置模型会让"拷一个 exe 就能用"破功
- **不使用 tokio / 单二进制 / 仅 Windows / 不做常驻服务注册**
- **`opt-level=3` + LTO + strip**（覆盖上游 `opt-level="z"`）

## 教训

1. **"调用方支持什么"必须先问清，再定传输层。** 这是需求调研的缺口，不是编码问题——写下 F-3.1 时没有确认过任何真实调用方的技术栈。
2. **"可选/默认关闭"的功能要警惕。** v1.0 把 HTTP 标成"可选备用"，实质是把最需要它的人排除在外。一个功能如果只有"不方便的人"才用，那它就是必需品，不是可选项。
3. **优雅不等于可用。** Named Pipe 在延迟和安全性上全面优于回环 HTTP，但对目标用户群不可达。对附属工具而言，**可达性优先于优雅**。
